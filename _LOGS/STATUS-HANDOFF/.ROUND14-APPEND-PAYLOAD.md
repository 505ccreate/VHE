### R14·1 — Reconciler adoption still does not fence the stale job worker; two polling owners can exist

Round 13 correctly added a reconciler lease, but the lease controls **reconciler-vs-reconciler** races
only. It does not control **reconciler-vs-job-worker** races.

The conflict is concrete:

- R13·1 makes an `accepted`/`in_flight` operation adoptable when its owning job is `running` with a
  heartbeat older than 120 seconds.
- The shipped §4.2 claim in `packages/jobs/worker.ts:35-45` admits that **same stale `running` job** using
  the **same 120-second predicate** (`:39-40`) and moves it back into execution.
- R13·1's CAS only tests `reconciler_owner_id` / `reconciler_lease_expires_at`; the ordinary worker does
  not participate in that fence.

Therefore a reconciler can adopt the provider operation at the same moment a replacement §4 worker
reclaims the stale job. Both can then believe they are the poll owner. The round-13 single-winner test
covers N reconcilers racing each other, but not this second ownership system.

Round 13 also leaves `$lease` undefined, leaves the reconciler-instance identity source undefined, and
stores ownership on `provider_operations` without binding the lease to the exact
`current_attempt_id`. A later explicit retry on the same permanent operation row can therefore inherit a
lease whose scope was the previous attempt unless application code invents a clearing rule.

**Binding correction — ONE poll-ownership fence shared by jobs and reconcilers, scoped to the exact
provider attempt.**

- Replace the reconciler-only ownership concept with a unified poll lease on the **current provider
  operation attempt**. `provider_operation_attempts` gains:
  - `poll_owner_kind TEXT NULL CHECK (poll_owner_kind IN ('job','reconciler'))`;
  - `poll_owner_token TEXT NULL` — a fresh ULID minted when ownership is acquired, never the job id or a
    process hostname;
  - `poll_lease_expires_at TIMESTAMPTZ NULL`;
  - `poll_generation INT NOT NULL DEFAULT 0`.
- **Lease duration is exactly 120 seconds and renewal cadence is 30 seconds**, deliberately reusing the
  shipped §4 heartbeat/takeover timing rather than introducing a second stale-owner definition.
- **Every provider poll — job worker or reconciler — must first own this same lease.** Acquisition/takeover
  is one CAS on the exact `provider_operation_attempts.id`; it sets a new `poll_owner_token`, increments
  `poll_generation`, and returns both. Renewal and every poll-result write are guarded by **attempt id +
  owner token + generation**. A zombie owner whose lease was replaced cannot write itself back into
  authority.
- R13·1's `reconciler_owner_id`, `reconciler_lease_expires_at`, `reconciler_adopted_at`, and
  `reconciler_generation` columns on `provider_operations` are **RETRACTED**. Reconciler adoption is not
  a second ownership system; it is acquisition of the same attempt-scoped poll lease with
  `poll_owner_kind='reconciler'`.
- The reconciler scan still uses R13·1's two adoption predicates (terminal owner, or stale `running`
  owner), but **winning the scan does not grant poll authority until the attempt-level CAS succeeds**.
  A stale §4 worker that also wakes must acquire that same CAS; exactly one side can poll.
- A new provider attempt starts with no poll owner and cannot inherit the prior attempt's lease because
  the lease lives on the attempt row itself.

### R14·2 — `continuation_generation` still depends on an undefined "original decision key"

Round 13 fixed the undefined phrase "continuation generation" but left the other input to the key
undefined for this path:

`routing_attempt_key = f(job_id, original decision key, continuation_generation)`.

The only earlier **decision key** definition is the client-supplied key for an operator rerun
(R7·6). A follower continuation after a proven `preaccept_rejected` / confirmed-no-job outcome is caused
by an outbox wake and can occur without an operator rerun. Nothing states which durable field is its
"original decision key". An implementer still has to invent key material at the exact place where
idempotency must be deterministic.

**Binding correction — remove the undefined input.**

- The continuation key is derived only from durable identities that exist on this path:
  **`routing_attempt_key = H('continuation-v1', job_id, prior_follower_routing_attempt_id,
  continuation_generation)`** using the project's canonical deterministic-key encoder/hash convention.
- `prior_follower_routing_attempt_id` comes from the exact active `provider_operation_followers` row
  linked to the parked job; no client value and no mutable queue field participates.
- `continuation_generation` is incremented by `UPDATE jobs SET continuation_generation =
  continuation_generation + 1 ... RETURNING continuation_generation` **inside the same transaction that
  wins the continuation wake** (R14·3 below). It is never incremented by a losing duplicate delivery.
- R13·2's phrase **"original decision key" is RETRACTED for follower continuations**. Operator reruns keep
  their existing decision-key semantics; this correction does not change that path.

### R14·3 — `consumed_at` has two incompatible transaction boundaries

R12·3 says the worker writes `job_wakeup_outbox.consumed_at` in the **same transaction as the successful
resume claim**. R13·3 then says `consumed_at` and the **outcome of the work the delivery triggered** always
commit together, including the budget-funded / budget-refused continuation branch. Those are not the same
transaction unless the spec explicitly makes them one; it never does.

This matters because the bad interleaving is exactly the lost-wake case R13·3 was trying to close: a
transaction can win `awaiting_provider_operation → running`, mark the wake consumed, commit, and then die
before the continuation routing attempt/reservation is durably installed. The target is now `running`,
the wake is consumed, and no new funded continuation exists.

**Binding correction — one DB transaction owns a continuation wake from claim through durable next
state.**

For `wake_kind='resume_provider_follower'`, one short Postgres transaction performs, in order:

1. lock/read the outbox row and verify `consumed_at IS NULL`;
2. win the exact follower resume claim and set the durable continuation marker;
3. load/lock the exact active follower attachment + current operation outcome;
4. if the outcome requires a new paid continuation, increment `continuation_generation`, claim/insert the
   new routing attempt, run the budget reservation decision, and install the new execution binding **or**
   commit the budget-refused terminal branch (R14·4);
5. resolve/re-park the follower relationship and set the job's durable next state appropriate to that
   outcome;
6. write `consumed_at=now()` **last**, in that same transaction.

No provider/network call occurs inside this transaction. A crash before COMMIT consumes nothing; a COMMIT
means the next durable state is already installed. R12·3 and R13·3 are superseded only as to this exact
transaction boundary; their at-least-once/reissue semantics remain.

The same invariant applies to the other continuation wake kinds: **a wake is not consumed merely because
`running` was written; it is consumed only in the transaction that durably installs the state from which
execution can safely continue or remain parked.**

### R14·4 — the budget-refusal branch has no legal routing-attempt state and contradicts the FK ordering

R13·3 says "the reservation attempt happens first," but the governing routing schema from R8·3 requires
`budget_reservations.routing_attempt_id` to reference an already-created `routing_attempts(id)`. R12·5
also explicitly orders **routing-attempt insert before reservation**. R13·3 itself acknowledges the
contradiction by saying *"if a routing-attempt row was inserted before the refusal was known"*.

Worse, R13·3 now wants that unfunded routing-attempt row retained as non-executable history, but the
closed R8·3 state set is only `reserved | walking | accepted | exhausted | abandoned`. It never says
which legal state represents "budget refused before this walk was funded." Leaving the row present with
an invented state or a false `reserved` state is not implementable.

**Binding correction — exact ordering and exact state.**

- Extend `routing_attempts.state` with **`budget_refused`** (terminal, non-executable).
- In the R14·3 transaction, the exact order is:
  1. compute the deterministic `routing_attempt_key` and first check for an already-committed attempt with
     that key; if one exists, replay its durable state instead of making a second budget decision;
  2. otherwise lock the owner's budget row and compute the funding decision **without inserting a
     reservation yet**;
  3. if funded, claim-on-insert the routing attempt directly as `reserved`, insert the held reservation
     referencing that attempt id, then install the execution binding — all before COMMIT;
  4. if refused, claim-on-insert the routing attempt directly as `budget_refused`, insert **no** reservation,
     install **no** execution binding, resolve the follower attachment, clear the continuation marker, set
     the job `failed/BUDGET_EXCEEDED`, and consume the wake — all before COMMIT;
  5. if the deterministic attempt insert loses a uniqueness race, re-read the winner and replay that
     winner's durable state; do not make a second reservation or submission.
- There is no invented pre-funding state and no committed `reserved` row without its held reservation;
  the attempt + reservation/binding (funded) or the `budget_refused` outcome (refused) become visible
  atomically.
- A duplicate delivery/key that finds terminal `budget_refused` reproduces the already-committed refusal;
  it does not reserve or submit.

This replaces R13·3's "reservation attempt happens first" wording and its undefined "non-executable
because nothing binds" state.

### R14·5 — R13·4 changed the direct-ledger grain but did not create a data channel capable of filling it

R13·4 correctly observes that one shipped `walkChain()` execution can touch multiple provider candidates
inside one `execution_attempt`, and changes the direct-ledger grain to
`(job_id, execution_attempt, provider_attempt_no)`.

But the data plumbing still cannot produce those rows:

- The round-12 authorized typed failure/result contract carries one provider/operation reference, one
  disposition, one charge state, and one cost. It does **not** carry `provider_attempt_no` and does not
  describe a list of earlier billed candidate outcomes.
- Shipped `walkChain()` (`packages/providers/routing.ts:115-136`) catches failed candidates internally and
  returns only a `ChainFailure` trail with `connectionId`, `providerSlug`, `errorCode`, and `error` — no
  submission disposition, charge state, provider charge id, billed cost, or candidate ordinal contract.
- The shipped `JobHandler` success result (`worker.ts:23-28`) has one `costCents` and one `providerId`.
  Therefore a billed candidate that fails and falls through before a later success is **swallowed inside
  the handler boundary**; the §4 worker cannot reconstruct the multiple ledger rows R13·4 now requires.

R13·4's chosen schema therefore "records reality" only if a second, unspecified event channel is
invented during implementation.

**Binding correction — the §4.2 amendment reserved as `0034` must carry per-candidate charge events, not
one scalar charge.**

Define one transport shape used by both success and failure outcomes:

```ts
type ProviderChargeEvent = {
  providerAttemptNo: number;          // 0-based ordinal in the frozen chain snapshot
  providerConnectionId: string;       // always present for a direct provider attempt
  providerOperationRef?: string;      // when the provider exposes one
  providerChargeId?: string;          // when the provider exposes a stable billing id
  submissionDisposition: 'preaccept_rejected' | 'accepted' | 'ambiguous';
  chargeState: 'none' | 'known' | 'unknown';
  costCents?: number;                 // required iff chargeState === 'known'
  errorCode?: string;
};
```

- The typed handler result/failure contract carries **`chargeEvents: ProviderChargeEvent[]`** plus its
  normal output/error fields. Every candidate touched by the handler contributes exactly one event.
- The chain walker/adapter boundary must preserve the frozen candidate ordinal and structured submission
  result; a plain `ChainFailure` string record is not sufficient for the amended §4.2 accounting path.
- The §4 transaction writes every `chargeState='known'` billed event under the R13·4 grain before retry or
  termination, then recomputes `jobs.cost_cents` from the reconciled ledger sum. Any `accepted` or
  `ambiguous` event with `chargeState='unknown'` parks for reconciliation and blocks automatic retry as
  round 12 already requires.
- **`provider_connection_id` is NOT NULL for every `origin='direct'` ledger row**, not only when
  `provider_charge_id` happens to be present. R13·5's scoped secondary guard remains
  `UNIQUE (provider_connection_id, provider_charge_id) WHERE provider_charge_id IS NOT NULL`.
- R13·4's `provider_attempt_no` rule remains, but it is now actually carried across the handler/worker
  boundary that writes the ledger.

This correction does **not** authorize editing VHE-2 yet. It defines what the already-authorized `0034`
blueprint amendment must include after this spec clears review.

### R14·6 — round 13's test reconciliation does not exercise the new cross-system invariants above

Round 13's tests are individually sensible but they can all pass while R14·1–R14·5 remain broken: the
reconciler race test races reconcilers only; the continuation test assumes key inputs exist; the refusal
test inspects the post-commit shape without pinning the transaction boundary/state; and the direct-ledger
test assumes the worker somehow receives per-candidate billing facts.

**Required round-14 tests (additive to the surviving test list):**

1. **Job-vs-reconciler poll race:** a stale accepted owner job and N reconcilers race the same attempt;
   exactly one attempt-scoped poll lease wins. A loser and a zombie holder both fail a generation-guarded
   result write. Provider poll counter == 1.
2. **Attempt scope:** after an adopted attempt resolves and an explicit retry creates a new attempt, the
   old poll token/generation cannot poll or write the new attempt; the new attempt begins unowned.
3. **Continuation-key provenance:** a follower continuation with **no operator decision key** produces a
   deterministic key from `(job_id, prior_follower_routing_attempt_id, continuation_generation)`; two
   deliveries of that one wake produce one generation and one routing attempt.
4. **Crash boundary:** crash after the SQL resume predicate would have matched but before transaction
   COMMIT ⇒ `consumed_at` remains NULL and no partial continuation state is visible. Crash after COMMIT ⇒
   `consumed_at` is non-null and the funded/parked/terminal next state is already durable.
5. **Budget refusal state:** cap refusal leaves one `routing_attempts.state='budget_refused'`, zero held
   reservations, zero execution bindings to that attempt, resolved follower attachment,
   `failed/BUDGET_EXCEEDED` job, cleared continuation marker, and consumed wake — all from one commit.
6. **Direct multi-candidate billing transport:** one execution attempt produces candidate 0 = known billed
   failure and candidate 1 = success. The handler boundary returns two `chargeEvents` with ordinals 0/1;
   two direct ledger rows are written with their provider connection ids and `jobs.cost_cents` equals the
   sum.
7. **Unknown direct charge blocks retry:** any event `accepted|ambiguous + chargeState='unknown'` parks for
   reconciliation before BullMQ retry/fall-through; no later candidate/provider call occurs.
8. **Scoped charge id still holds:** the same `provider_charge_id` may exist on two different provider
   connections, but duplicates on the same connection are rejected; every direct row has a non-null
   `provider_connection_id` even when `provider_charge_id` is NULL.
